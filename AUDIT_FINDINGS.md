# Limo — Comprehensive Code Audit

Scope: first-party source under `src/` (core engine, network/remote, archive parsers, crypto, all UI), plus tests, CI, packaging and dependencies. ~65k LOC, C++/Qt6.

**Method:** 29 subsystem reviewers (deep read of every file) → adversarial verification of every Critical/High/Security finding. Totals: 261 live findings + 29 investigated-and-refuted. Severity uses the verifier-adjusted value where a finding was verified.

### Security (8)

- **`src/core/cyberpunkredmod.cpp:198-205`** — Path traversal via untrusted REDmod name when copying into game_root/mods/<name> _(verified ✓)_
  - **Category:** Security · **Severity:** High _(adjusted from Critical)_
  - **Issue:** In layoutRedMods(), the destination directory is built as `const sfs::path dest = mods_dir / mod->name;` where mod->name comes directly from the mod-controlled info.json "name" field (parseRedMod reads info["name"].asString() with no validation beyond non-empty). std::filesystem operator/ does NOT normalise or contain the right-hand operand: a name like "../../../../home/user/.config/limo" traverses out of mods_dir, and an absolute name like "/home/user/important" REPLACES the path entirely. The code then runs `sfs::remove_all(dest, ec)` followed by `sfs::copy(source_path, dest, recursive | overwrite_existing)`. A malicious mod archive can therefore cause arbitrary directory deletion (remove_all) and arbitrary file overwrite outside the intended mods directory. The same unvalidated name is also written into MODS.json (writeLoadOrderFile) and used as the mods/<name> destination, so the attack triggers during the normal 'Deploy REDmods' flow (buildRedmodDeployCommand -> layoutRedMods).
  - **Fix:** Reject or sanitise mod->name before using it as a path component: in parseRedMod, return nullopt if the name contains a path separator ('/' or '\\'), is exactly "."/"..", is absolute, or contains ".." path elements. Alternatively, in layoutRedMods compute dest = (mods_dir / name).lexically_normal() and verify it is still under mods_dir (std::mismatch on the normalised paths) before any remove_all/copy.
  - **Verifier:** Confirmed: mod.name is read raw from mod-controlled info.json (cyberpunkredmod.cpp:102, only checked non-empty) and used as `dest = mods_dir / mod->name` (line 198) before `sfs::remove_all(dest)` (line 200) and `sfs::copy(..., overwrite_existing)` (line 203); std::filesystem operator/ does not normalize, so an absolute name replaces the path and `../` segments escape mods_dir when the OS resolves them, enabling arbitrary deletion/overwrite. The path is reachable in the real deploy flow (applicationmanager.cpp:1105 -> buildRedmodDeployCommand -> layoutRedMods), and no sanitization exists anywhere in the chain; severity adjusted to High since it requires the victim to install and deploy a malicious REDmod archive rather than being remote/zero-interaction.

- **`src/core/lspakfilelistentry.h:17`** — Out-of-bounds read: non-NUL-terminated path[256] from untrusted .pak read as C-string _(verified ✓)_
  - **Category:** Security · **Severity:** High
  - **Issue:** LsPakFileListEntry.path is a fixed char[256] populated by reinterpret_cast directly from decompressed, attacker-controlled .pak file-list bytes (lspakextractor.cpp:217-218). It is later converted to a std::filesystem::path via `f.path` in LsPakExtractor::getFileList (lspakextractor.cpp:138, `path_list.emplace_back(f.path)`), which constructs from a const char* and reads until a NUL byte. A malicious BG3 .pak can fill all 256 bytes with no NUL, so the path constructor reads past the array into adjacent struct fields and the heap buffer, producing an out-of-bounds read (info leak / potential crash) on a mod-controlled archive parsed automatically by Bg3Deployer.
  - **Fix:** Treat the field as bounded: construct the path/string with an explicit length, e.g. std::string(entry.path, strnlen(entry.path, sizeof(entry.path))), and reject entries whose 256 bytes contain no terminator. Do this where LsPakFileListEntry is materialized in getFileList().
  - **Verifier:** Confirmed: LsPakFileListEntry.path (char[256], lspakfilelistentry.h:17) is filled verbatim by reinterpret_cast from decompressed, mod-controlled .pak bytes (lspakextractor.cpp:217-218) with no NUL-termination check anywhere in readFileList/getFileList, and getFileList() at line 138 does path_list.emplace_back(f.path). I empirically verified with ASan that std::filesystem::path's char[N] constructor decays to a string_view via std::char_traits::length (strlen), so a path with all 256 non-NUL bytes triggers an out-of-bounds read past the array into adjacent struct/heap memory. The archive is auto-parsed by Bg3PakFile::init (Bg3Deployer) on untrusted BG3 mods, so input is genuinely attacker-controlled; this is a real heap OOB read (info leak / crash).

- **`src/core/plugindeployer.cpp:678-689`** — Integer overflow in TES3 master parser permits out-of-bounds read on malformed plugin _(verified ✓)_
  - **Category:** Security · **Severity:** High
  - **Issue:** In readPluginMasters' TES3 branch, the subrecord size is read as a full 4-byte uint32 (readLE(...,4)).   - **Verifier:** Confirmed at src/core/plugindeployer.cpp:678-689: in the TES3 branch `size` is read as a full 4-byte uint32 (line 682) and the guard `if(pos + size > data_size)` (line 684) is done in uint32 arithmetic. - **`.github/workflows/release.yml:113-118`** — linuxdeploy downloaded from unpinned 'continuous' release with no checksum/signature verification _(verified ✓)_
  - **Category:** Security · **Severity:** Medium _(adjusted from High)_
  - **Issue:** The release job downloads linuxdeploy-x86_64.AppImage and linuxdeploy-plugin-qt-x86_64.AppImage from the GitHub 'continuous' (rolling) release tag and immediately chmod +x and executes them to package the published artifact. The 'continuous' tag is mutable and the binaries are never verified against a known checksum or signature. A compromise of the linuxdeploy repo/release, or a MITM able to serve a malicious AppImage, would result in arbitrary code running in the release pipeline and being baked into the Limo AppImage that users download. This is the published-artifact supply chain, so the blast radius is every release consumer.
  - **Fix:** Pin to a specific linuxdeploy release tag (not 'continuous') and verify a SHA256 checksum before chmod/exec, e.g. download the matching .sha256 (or hardcode the expected hash) and run `sha256sum -c` and abort on mismatch. Optionally vendor a known-good copy.
  - **Verifier:** Lines 116-117 wget linuxdeploy and its Qt plugin from the mutable 'continuous' GitHub release tag with no SHA256/signature verification, then line 118 chmod +x and the Build AppImage step executes them to produce the very AppImage attached to the public GitHub Release (lines 164-174), so the input is genuinely third-party/network-controlled and the published-artifact supply-chain risk is real. I lower severity to Medium because the download is over HTTPS to GitHub (TLS largely neuters the MITM scenario), leaving the residual risk as upstream/release compromise of a widely-used reputable tool, and 'continuous' is the only tag linuxdeploy publishes (no immutable pinned artifact exists), so the practical fix is checksum-pinning rather than tag-pinning.

- **`src/core/cryptography.cpp:142-145`** — Weak key derivation: master password byte-repeated to 32 bytes with no KDF or salt _(verified ✓)_
  - **Category:** Security · **Severity:** Medium _(adjusted from High)_
  - **Issue:** encrypt() (and decryptWithKey()) build the AES-256-GCM key by repeating the raw user password bytes: `key_padded[i] = actual_key[i % actual_key.size()]`. There is no salt, no PBKDF2/scrypt/Argon2, and no stretching. A short master password (e.g. 4-8 chars) is simply tiled to 32 bytes, so the effective key space equals the password's, the key bytes are periodic, and the same password always yields the same key.   - **Verifier:** The code at src/core/cryptography.cpp:142-145 (encrypt) and 202-205 (decryptWithKey) derives the AES-256-GCM key by byte-tiling the raw value with key_padded[i] = actual_key[i % actual_key.size()] — no salt, no PBKDF2/scrypt/Argon2, no stretching. Callers (settingsdialog.cpp:383, changeapipwdialog.cpp:72, enterapipwdialog.cpp:40) pass the user's master password as this key to protect a Nexus API key whose cipher/nonce/tag are stored in plaintext QSettings (info_c/info_n/info_t), so an attacker with the config file can brute-force a short password offline (the GCM tag makes each guess verifiable). It is a genuine weakness; I downgrade to Medium because the protected asset is a Nexus mod API key, the attack requires local read access to the config, and the no-password path already uses a per-installation random key.
